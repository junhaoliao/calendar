## Design review summary (context for the maintainer)

- Run 1: the core design is sound and kept: one pure, synchronous resolver shared by preview and commit, with `defaultResult` as the built-in fallback and a controlled `onEventUpdate`.
- Run 1: keep the resolver synchronous. Async or server validation belongs at commit time: apply optimistically in `onEventUpdate` and roll back on failure.
- Deferred direction: `resolveEventResize` with the same contract. Endpoint resizing currently bypasses host policy. Plan 003's `MoveResolution` and `rejection` state are meant to be reused for it.
- Run 2: the transparent-source design is a good simplification. It deletes the
  morphing drag card and reuses the destination pipeline, so preview and commit
  share one layout path. Its gaps were all in **non-accepted** states (refused or
  off-grid hovers), which no test covered. Plans 006–008 close them.
- Run 2 direction, not planned: give the hovered slot a destructive ring when the
  outcome is refused. Today `calendar-drop.tsx:67` uses the same `bg-accent` ring
  for accepted and refused targets. Signal it from `TimeColumn`/`MonthCell`, not
  by subscribing all ~672 slots to drag state.
- Run 2 direction, not planned: localize dnd-kit's `screenReaderInstructions`
  (`aria-describedby` text, English, says "press space again to drop" while
  `docs/API.md` documents Enter). This needs plugin options that follow the
  locale, so it is a separate design.

## Findings considered and rejected

- **Rewrite the resolution cache's shallow field comparison** (`use-calendar-controller.ts` `resolveDrag`). It deliberately supports hosts that mutate events in place, and a unit test pins that behavior. It's more complex than needed, but correct; not worth churn.
- **Per-target re-render cost of `useMovePreview`** in Month/Time views. `useDragOperation` only re-renders on source/target changes (one per 15-minute slot), not on pointer moves, so the cost is acceptable. Run 2 re-checked this: the change moved the hook from `DraggableEvent` into every `EventItem`, which adds only static variants that never drag, so the verdict is unchanged.
- **The `renderEvent` wrapper's unstable identity** (`src/event-calendar.tsx:37-48`). This predates the feature and has the same class of issue as plan 001. Its dependencies need i18n-boundary design; it's a candidate for a separate plan.
- **"117 extra modified files" in `git status`.** These are stat-only line-ending noise from `core.autocrlf=true`. Committed and working contents are identical (`git diff` shows only the 28 real files), so nothing to fix. Adding `.gitattributes` (`* text=auto eol=lf`) is optional hygiene.
- **Run 2: stale `data-dragging` attribute** on `EventSurface` (`event-item.tsx:112`). No CSS or test reads it since the drag-card styles were removed. It is harmless and trivial.
- **Run 2: two hide mechanisms for the move source**: inline `opacity`/`pointerEvents` in `DraggableEvent` plus the `.calendar-event-wrap[data-move-source]` CSS rule. Redundant but harmless, and popover rows (which have no wrap) need the inline path.
- **Run 2: deleting `event-drag-style.test.ts`.** This is justified: the helper it tested is gone, and the behaviors it covered (destination height, midnight segments) are now asserted by browser tests against the real preview pipeline.
